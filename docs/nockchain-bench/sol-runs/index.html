How To Read These Numbers (Pedagogical Explainer)

      
First, what is a tuple on this page? It is one benchmark cell identified by (environment, branch, fixture) in one run. Example: (docker, btree, v1).

      
For each tuple, the model estimates p(change): the probability that this tuple's throughput has a real persistent shift (not just normal run-to-run noise). The starting signal is a throughput z-score, which says how far today's throughput is from baseline in units of baseline spread. Roughly: z=0 is typical, larger |z| means more unusual.

      
Raw probabilities are then calibrated using prior resolved tuples so reported percentages match observed frequencies better. This is done with isotonic calibration (a monotonic remapping learned from historical prediction/outcome pairs).

      
Confidence is the probability that the displayed class is correct. For classes regression or improvement, confidence is p(change). For class stable, confidence is 1 - p(change).

      
Brier score measures probability error using squared loss: for each resolved tuple, error is (p - y)^2, where p is predicted probability and y is the actual outcome (1 means persistent change happened, 0 means it did not). The page reports the mean of this error. Example: predicting 0.80 when y=1 gives 0.04; predicting 0.80 when y=0 gives 0.64.

      
Reliability curve: we group predicted probabilities into ranges called bins. A 0.1-wide bin is a 10-point probability interval, like [0.2, 0.3) or [0.7, 0.8). For each bin, we compare (1) the average predicted probability vs (2) the observed positive rate (how often change actually happened). Perfect calibration is the diagonal line y=x.

      
ECE (Expected Calibration Error) compresses that curve into one number: in each bin, compute the absolute gap between predicted and observed rate, weight by that bin's sample share, and sum: ECE = sum_k (n_k / N) * |acc_k - conf_k|. Lower is better; 0 means perfect calibration on the evaluated data.

      
Labeling rule for calibration: each tuple is resolved only after a fixed future window of runs (currently 3). If later runs support a persistent out-of-band shift for that tuple, label is positive. Before enough future runs exist, labels are pending, so calibration statistics are intentionally sparse right after rollout.
