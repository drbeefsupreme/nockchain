# Codebase Structure

**Analysis Date:** 2026-02-24

## Directory Layout

```text
nockchain/
├── crates/             # Rust workspace crates (runtime, apps, adapters, tools)
├── hoon/               # Hoon source used to build kernel jam assets
├── assets/             # Built jam artifacts consumed by binaries
├── scripts/            # Operational and benchmarking shell/python scripts
├── docs/               # Benchmark outputs and planning docs
├── .github/workflows/  # CI and release automation
├── Cargo.toml          # Workspace root and dependency graph
├── Makefile            # Build/test/install orchestration
└── rustfmt.toml        # Formatting configuration
```

## Directory Purposes

**`crates/`:**
- Purpose: Hold all buildable Rust components in the workspace.
- Contains: Binaries, libraries, protocol adapters, kernel packages, developer utilities.
- Key files: `crates/nockchain/src/main.rs`, `crates/nockapp/src/nockapp/mod.rs`, `crates/nockchain-libp2p-io/src/driver.rs`, `crates/nockapp-grpc/src/services/public_nockchain/v1/driver.rs`, `crates/bridge/src/main.rs`.

**`crates/kernels/`:**
- Purpose: Package kernel jam bytes as Rust crates.
- Contains: Kernel-specific `lib.rs` exports for app composition.
- Key files: `crates/kernels/dumb/src/lib.rs`, `crates/kernels/miner/src/lib.rs`, `crates/kernels/wallet/src/lib.rs`, `crates/kernels/bridge/src/lib.rs`, `crates/kernels/nockchain-peek/src/lib.rs`.

**`hoon/`:**
- Purpose: Source tree for Hoon programs compiled into jam artifacts.
- Contains: Apps, common helpers, test jams, data fixtures.
- Key files: `hoon/apps/`, `hoon/common/`, `hoon/dat/`, `hoon/jams/`.

**`assets/`:**
- Purpose: Built kernel jams consumed by binaries and installation targets.
- Contains: Jam files generated by Make targets.
- Key files: `assets/dumb.jam`, `assets/miner.jam`, `assets/wal.jam`, `assets/peek.jam`, `assets/bridge.jam` (generated via `Makefile`).

**`scripts/`:**
- Purpose: Operational scripts for node startup and SOL benchmark workflows.
- Contains: Runtime launch scripts and benchmark pipeline helpers.
- Key files: `scripts/run_nockchain_node.sh`, `scripts/run_nockchain_miner.sh`, `scripts/sol_bench_matrix.sh`, `scripts/sol_guard_ci.sh`.

**`docs/`:**
- Purpose: Benchmark artifacts and planning outputs.
- Contains: SOL run reports/manifests and plan notes.
- Key files: `docs/nockchain-bench/sol-runs/`, `docs/plans/`.

## Key File Locations

**Entry Points:**
- `crates/nockchain/src/main.rs`: Main chain node binary entry.
- `crates/nockchain-api/src/main.rs`: API-focused node entry.
- `crates/bridge/src/main.rs`: Bridge runtime entry.
- `crates/nockchain-wallet/src/main.rs`: Wallet CLI entry.
- `crates/nockchain-peek/src/main.rs`: Peek utility entry.
- `crates/nockchain-explorer-tui/src/main.rs`: Explorer TUI entry.

**Configuration:**
- `Cargo.toml`: Workspace composition and shared dependencies.
- `Makefile`: Build/install/test and asset generation commands.
- `rustfmt.toml`: Rust formatting settings.
- `example-nockapp.toml`: NockApp example config.
- `example-registry.toml`: Registry example config.

**Core Logic:**
- `crates/nockapp/src/nockapp/mod.rs`: Runtime loop, save logic, signal/exit handling.
- `crates/nockapp/src/nockapp/driver.rs`: Driver API (`NockAppHandle`, `IOAction`).
- `crates/nockapp/src/kernel/boot.rs`: Kernel boot, CLI, tracing initialization.
- `crates/nockchain/src/lib.rs`: Node assembly and driver wiring.
- `crates/nockchain-libp2p-io/src/driver.rs`: libp2p swarm adapter.

**Testing:**
- `crates/*/tests/`: Integration/property tests by crate.
- `crates/nockapp-grpc/src/tests.rs`: gRPC crate tests.
- `crates/nockchain-libp2p-io/src/cbor_tests.rs`: codec-focused tests.
- `crates/bridge/src/main.rs`: embedded test module for bridge flow and config constraints.

## Naming Conventions

**Files:**
- Use `snake_case.rs` for module files (examples: `crates/nockchain/src/mining.rs`, `crates/bridge/src/proposal_cache.rs`, `crates/nockchain-libp2p-io/src/p2p_state.rs`).
- Use `main.rs` for binaries and `lib.rs` for crate roots (examples: `crates/nockchain/src/main.rs`, `crates/nockapp/src/lib.rs`).
- Use versioned module directories for protocol surfaces (examples: `crates/nockapp-grpc/src/services/public_nockchain/v1/`, `crates/nockchain-types/src/tx_engine/v1/`).

**Directories:**
- Use top-level crate-per-capability layout under `crates/` (examples: `crates/nockapp/`, `crates/nockchain/`, `crates/bridge/`).
- Use nested capability submodules for large domains (examples: `crates/nockapp/src/nockapp/actors/`, `crates/nockchain-bench/src/speed_of_light/guard/`).

## Where to Add New Code

**New Feature:**
- Primary code: add to the owning app or adapter crate under `crates/<domain>/src/` (for node runtime features use `crates/nockchain/src/`; for runtime-generic features use `crates/nockapp/src/`; for network protocol handling use `crates/nockchain-libp2p-io/src/`).
- Tests: add crate-local tests in `crates/<domain>/tests/` or module tests in the touched source file.

**New Component/Module:**
- Implementation: create a new `snake_case.rs` module under the relevant crate and register it in that crate root (`crates/<domain>/src/lib.rs` or `crates/<domain>/src/mod.rs`).

**Utilities:**
- Shared helpers: place cross-cutting runtime helpers in `crates/nockapp/src/utils/`.
- Protocol/data helpers: place shared chain-domain utilities in `crates/nockchain-types/src/` or `crates/nockchain-math/src/`.
- CLI/tooling helpers: place build/dev support in `scripts/` (shell/python) or `crates/nockup/src/` (Rust CLI).

## Special Directories

**`crates/nockvm/`:**
- Purpose: Embedded VM subtree with its own docs/resources and nested Rust workspace content.
- Generated: No.
- Committed: Yes.

**`bench-artifacts/`:**
- Purpose: Benchmark matrix outputs and generated profiling artifacts.
- Generated: Yes.
- Committed: Yes (currently present in repository state).

**`target/`:**
- Purpose: Cargo build output directory.
- Generated: Yes.
- Committed: No (build artifact directory).

**`.planning/codebase/`:**
- Purpose: Codebase mapping documents consumed by planning/execution commands.
- Generated: Yes (by mapper commands).
- Committed: Yes (intended planning metadata).
